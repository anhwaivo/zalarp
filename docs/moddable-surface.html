Tested — server-enforced proven

The client gate lifts (request gets sent / UI stops blocking), but Zalo's server re-validates and rejects. These produce nothing real — verified by actual testing, not theory.

Message pin limit sig

Client pin of limit_pin_messages (5 → 9999) was built and tested — still capped at 3. The cap doesn't even read that config key: the pin UI shows pinLimitNumber, a per-conversation value the server pushes. The client never consulted the patched default.

TESTED — server-side. Cap came from server state (3, not the local default of 5). Client patch produces nothing.

Send all file types sig

Emptying unsupportFile (exe/cmd/bat/com/lnk/vbs) lifts the client-side isValidFile reject so the upload request sends — but the server independently refuses dangerous extensions.

TESTED — server-side. Client gate lifted, upload still refused by server.

Recall window (edit/unsend own msgs past cutoff) sig

Pinned recallMessageMaxTime (300s) + time_enable_edit_undo_msg (120s) on the Ze/NDmK config. The client did fire /api/message/undo past the window — server answered error 112 (isServerUndefinedError).

TESTED — server-side. Window is settings.chat.time_undomsg, server-supplied and server-rechecked.

zCloud storage / quota sig

isPaidUser() reads this.plan on CloudConfigv2 — a server response. Every upload re-checks quota server-side. A client flip would only fake the badge.

Server-side by design. Same shape as the three proven cases — the resource lives on Zalo's infra.

zBusiness / OA features sig

isBusinessAccount reads bizInfo.pkgId>0 — a server-stamped profile field. isOAVerified reads the profile cache. Cosmetic claim only; OA tools stay gated.

Server-side by design.

Calls / video calls sig

enableCall/enableVideoCall are set from settings.chat.enable_call — server config. Signaling (zcall.initCall, onCallSignal) is server-mediated. Button can be shown; the call can't complete.

Server-side by design.

Message length / file-count limits sig

limitMsgByte (3KB), maxNumberOfFile (9), limit_pin_messages, numSearchResultMessage are client constants — but user testing showed file-count isn't really capped (sent 15), so these defaults may not be the live gate at all. Server may enforce the real limits; untested which ones are client-only.

all in NDmK/Ze config — verify against a live server before building

The rule that emerged

  • If the resource lives on the client (theme, message cache, UI gates, quality-mode flags) → moddable.
  • If the resource lives on Zalo's server (quota, business features, call signaling, server-stamped limits/timestamps) → client patch only changes what the request attempts; the server re-validates and rejects. err 112 / silent cap / refused upload — same outcome every time.
  • Read the real source of a limit before patching. limit_pin_messages=5 looked like the pin cap but the UI capped at 3 — the live value was pinLimitNumber from server state. Patching the wrong constant does nothing.

Surveyed against Zalo PC 26.10.20 bundles; three of the "tested" entries were confirmed by live server attempts (112 error, pin still capping at 3, file upload refused). Webpack ids shift per release — all hooks are shape-matched and degrade to no-ops.
